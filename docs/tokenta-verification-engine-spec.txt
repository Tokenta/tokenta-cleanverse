1. EXECUTIVE SUMMARY
================================================================================

Tokenta's core product is not an API key marketplace UI. The traded commodity is:

    "Trusted API Asset State"

The value chain:

    Raw API Key  →  Verification Pipeline  →  Verified API Asset  →  Tradable Asset

The Verification Engine is Tokenta's primary technical moat. The Terminal (BUY/SELL,
F1–F7 workspaces) is the presentation layer; escrow, chat, and reputation depend on
verification outputs being correct, timely, and provable.

This document defines:
  - How each verification touchpoint in the current frontend maps to backend APIs
  - Why verification MUST be asynchronous (5–60+ seconds, multi-provider, rate limits)
  - Worker pipeline stages aligned with F2 "Verification Pipeline · Real-Time" UI
  - Provider-specific adapter strategy (OpenAI, Anthropic, Google, etc.)
  - Proof hashing for settlement/dispute evidence (not raw keys on-chain)
  - Security rules: ephemeral key handling, encryption, fingerprints only in logs

No code implementation is included. This is the execution blueprint for engineering.

6. ASYNC VERIFICATION ARCHITECTURE
================================================================================

WHY ASYNC (mandatory):

  - Provider latency: 200ms–30s per probe; multiple probes per job
  - Rate limits: Exponential backoff, per-provider concurrency caps
[IMPLEMENTED 2026-05-19 — partial] provider-limiter.ts (PROVIDER_MAX_CONCURRENT);
  BullMQ/redis/memory queues; global fair queue across regions TBD.
  - Multi-step pipeline: 5–12 stages with partial failure recovery
  - Rotation/fraud: May require delayed re-check (old key active after 7 days)
  - Scale: Status strip targets 400+ proofs/s network-wide

ANTI-PATTERN (forbidden):

  POST /verify → server blocks 30s → returns PASS

  This freezes Terminal UI and violates trust UX (no visible pipeline).

CORRECT PATTERN:

  POST /jobs → 202 Accepted { jobId }
  Client → SSE stream until terminal state
  Optional → GET /jobs/{id} for reconnect/poll fallback

Job SLA tiers:

  Tier          Target duration   Context
  ------------  ----------------  ---------------------------------
  FAST          < 15s             Pre-purchase spot check
  STANDARD      < 60s             Listing onboarding
  EXTENDED      < 180s            Rotation + fraud recheck
  CONTINUOUS    recurring         Tokenta Direct LIVE heartbeat

9. VERIFICATION WORKER PIPELINE (EXECUTION LAYERS)
================================================================================

Worker consumes: verification.jobs queue message { jobId }

Stage order (configurable per context):

  STAGE 0 — job_created
    Persist job, emit event, decrypt key in memory (KMS envelope)

  STAGE 1 — CONNECTIVITY (Layer 1)
    Provider adapter: health endpoint probe
    OpenAI example: GET /v1/models, Authorization Bearer
    Checks: HTTP 200, auth valid, latency, region/account metadata
    Output: { connectivity: PASS|FAIL, latencyMs, accountHints }

  STAGE 2 — QUOTA (Layer 2) — HARDEST
    Provider-specific strategies (see Section 10)
    Output: { verifiedQuantity, confidence: high|medium|low, method }

  STAGE 3 — RATE_LIMIT (Layer 2b)
    Infer limits from headers, 429 behavior, tier endpoints
    Output: { requestsPerMin, tokensPerMin, burst }

  STAGE 4 — ACCESS_METHOD (Layer 3)
    DIRECT_KEY: successful inference call
    PROXY_GATEWAY: heartbeat against Tokenta proxy edge
    KEY_ROTATION: compare old fingerprint vs new key probes

  STAGE 5 — RISK_ANALYSIS (Layer 4)
    See Section 12

  STAGE 6 — FINALIZE
    Canonical proof payload → SHA-256 → proofHash
    Sign with platform key
    Store proof record; update job PASSED|FAILED
    Zeroize apiKey from memory
    If LISTING_DRAFT: notify Listings service
    Emit job_completed | job_failed

Failure handling:
  - Retryable: 429, 5xx, timeout → exponential backoff max 3 per stage
  - Non-retryable: 401 invalid key → immediate FAILED
  - Partial PASS: buyback may offer resubmit at verified lower quantity

12. RISK ANALYSIS ENGINE
================================================================================

Inputs:
  - keyFingerprint (HMAC-SHA256 of key, platform pepper)
  - seller wallet address
  - provider account hints from connectivity
  - historical disputes, slashes, arbitration losses

Checks:

  1. Shared key detection
     Same fingerprint from multiple sellers → block or flag

  2. Blacklist
     Keys/accounts with prior fraud or provider ban

  3. Abnormal usage velocity
     Token burn rate vs declared inventory

  4. Reseller / gray market proxy
     Response headers, endpoint patterns (ties to GRAY_MARKET UI flag)

  5. Revocation risk score
     Heuristics for keys likely to be rotated/revoked by provider

Output:
  riskScore 0.0–1.0
  riskFlags: string[]
  recommendation: ALLOW | REVIEW | DENY

Feeds:
  - trustLabel on listings (92, TOKENTA GUARANTEED)
  - deposit requirements (150% P2P, 200% buyback)
  - F6 reputation events (VERIFY-FAIL, VERIFY-PASS-STREAK)

16. CONTINUOUS VERIFICATION NETWORK (PHASE 2+)
================================================================================

Beyond one-shot jobs:

  Scheduled heartbeat jobs per active listing / inventory SKU
  Intervals: 5 min (Tokenta Direct), 30 min (high-value P2P), 1 hour (standard)

  Worker lite pipeline: CONNECTIVITY + QUOTA quick probe

  State transitions:
    LIVE → STALE (no heartbeat 2x interval)
    STALE → REVOKED (provider 401)
    → UI: LIVE badge, verificationTimestamp "12s ago"

  Market impact:
    Auto-delist on REVOKED
    Buyer alerts on STALE
    Tokenta Direct: ops alert for replenishment

  This enables "real-time verified API market" positioning.
