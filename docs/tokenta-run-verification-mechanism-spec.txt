SYSTEM IDENTITY (v0.4):
  Tokenta RUN VERIFICATION is a constrained stochastic inference engine for API
  execution capacity — with economic throttling, adversarial safety controls, and
  multi-dimensional asset scoring. It is NOT a quota checker, API ping tool, or
  billing inspector.

  One-line engineering definition:
    Probabilistic inference of hidden variable "sustainable execution capacity now"
    under bounded real API consumption.

  Correct product sentence:
    "We run minimal real API samples to estimate whether this key can likely
     support the listing's capacity band — not your exact remaining balance."

  Wrong product sentences (prohibited in UI/legal copy):
    "We verify your remaining quota/balance."
    "We will use up to 3% of your quota each verification." (misleading — see 4G)
    "Zero-cost verification."

CORE PRINCIPLE:
  Consumption is unavoidable. Operational burn is capped by a nonlinear adaptive
  probe envelope (4G) + absolute call fuses — NOT by linear % of declared quantity.
  A separate consentDisclosureCeiling (formerly "3%") exists only for legal checkbox
  wording and must NOT drive probe authorization (4D).

Scope:          Provider probes, capacity inference, probe budgets, lock states,
                liability modes, risk scoring, evidence artifacts.
                Does NOT define queues, REST routing, or DB schema.

1. DEFINITION OF RUN VERIFICATION
================================================================================

RUN VERIFICATION is not a single HTTP call. It is a bounded, auditable SEQUENCE of
CONTROLLED SAMPLING against real provider APIs. Every probe that reaches the
provider may consume request quota (RPM) and, for inference micro-probes, real
input/output tokens charged to the seller's account.

Product framing (mandatory in UI, legal, and support docs):
  - NOT: "Zero-cost verification" | "Balance/quota verification" | "Exact remaining tokens"
  - YES: "Verifiable execution-capacity inference via controlled sampling"

Industry paradigm selected by Tokenta:
  Paradigm 1 — Liveness only: unreliable; cannot infer execution capacity.
  Paradigm 2 — Micro-probe sampling (THIS SPEC): industry standard; bounded token cost.
  Paradigm 3 — Full workload simulation: prohibitively expensive; out of scope.

Analogies (internal positioning only):
  - Credit scoring sample pull (not full credit report)
  - Fraud probe transaction (not full account drain)
  - Ad impression sampling (not full campaign spend audit)

Tokenta implements Paradigm 2 with: single-model lock, cache, adaptive sizing,
lock state machine, and liability split — so the system cannot become a
consumption attack surface against sellers.

RUN VERIFICATION answers four questions:

  Q1  AUTHENTICITY     Does this credential authenticate successfully right now?
  Q2  EXEC CAPACITY    Can this key execute inference consistent with the listing claim?
                      (probabilistic inference — NOT exact remaining balance)
  Q3  USABILITY        Can the declared access method (direct key, proxy, rotation) work?
  Q4  INTEGRITY        Is the seller's claim consistent with observed provider state?

Outputs (mechanism layer, before marketplace binding):

  estimatedExecutableQuantityRange   object   { min, max, band, unit } — PRIMARY quantity output
  declaredAlignment                  enum     CONSISTENT | UNDERCLAIMED | OVERCLAIMED | UNVERIFIABLE
  capabilityScore                    float    0.0-1.0 — can execute / sustain workload (9A)
  trustScore                         float    0.0-1.0 — fraud/shared-key/gray-market (9A)
  complianceScore                    float    0.0-1.0 — policy/region/ToS signals (9A)
  executionCapacityBand              enum     UNKNOWN | INSUFFICIENT | SUFFICIENT | ABUNDANT
  confidence                         enum     HIGH | MEDIUM | LOW (epistemic, not financial)
  terminalOutcome                    enum     PASS | FAIL | REVIEW | DEGRADED (9B)
  verificationMethod                 enum     DIRECT_KEY_TEST | PROXY_HEARTBEAT | ROTATION_VALIDATION
                                         | LIVENESS_ONLY | DEGRADED_PARTIAL
  costLiability                      enum     SELLER_PAID | PLATFORM_SUBSIDIZED | BUYER_TRIGGERED
  probeManifest                      object   Forensic log: probes, tokensUsed, requestsUsed, cacheHit
  verificationLockState              enum     See Section 4C (incl. PARTIAL_SUCCESS_DEGRADED)
  failureCode                        string   Machine-readable if FAIL
  failureMessage                     string   Human-readable for Terminal UI

  DEPRECATED (do not emit as primary; marketplace migration only):
  verifiedQuantity — point equality to declared is FORBIDDEN inference (v0.4).
  capacityInferenceScore — alias of capabilityScore for backward compatibility.
  riskScore — REMOVED as single gate; use trustScore + complianceScore (9A).

The Terminal shows step-by-step progress. Each step maps to one or more probes from
Section 2 paradigms. The worker MUST NOT return PASS without executing at least:

  - One AUTH probe (Layer 1)
  - One CAPACITY INFERENCE probe (Layer 2) OR documented LIVENESS_ONLY fallback
  - One POLICY probe (rate/entitlement) when provider supports it and lock allows

================================================================================
2. VERIFICATION MECHANISM PARADIGM (TAXONOMY)
================================================================================

All provider verification reduces to seven probe paradigms. Every RUN VERIFICATION
pipeline is a composition of these paradigms.

------------------------------------------------------------------------------
Paradigm A — LIVENESS AUTH (Near-Zero TOKEN Cost; May Consume REQUEST Quota)
------------------------------------------------------------------------------
Purpose:   Prove the key exists, is not revoked, and can reach the provider API.
Typical:   GET /v1/models (OpenAI), GET models (Gemini), minimal list/health.
           Anthropic: often combined with micro-probe (no public models list on all keys).
Cost:      Usually 0 completion/input/output tokens billed.
           DOES consume: RPM (requests per minute), and on some providers counts toward
           request quota or daily call limits. Must be counted in probeManifest as
           requestsUsed, not tokensUsed.
Latency:   100-800 ms typical.
Failure:   401 invalid key, 403 forbidden, 404 wrong base URL, timeout, TLS error.

When to use:  ALWAYS as first probe after key ingest (unless valid cache hit — 4B).
Tokenta step: CONNECTIVITY (Test 1/3 in buyback UI).

------------------------------------------------------------------------------
Paradigm B — ENTITLEMENT READ (Admin or Account Metadata)
------------------------------------------------------------------------------
Purpose:   Read organization tier, project, billing status, model allow-list.
Typical:   OpenAI organization usage API (requires admin key), Anthropic usage API.
Cost:      No inference tokens; may require separate admin credential (NOT seller key).
Limitation: Often NOT available with seller-submitted project keys.

When to use:  Platform inventory ingest, Tokenta Direct ops — not typical P2P seller flow.
Fallback:     Skip with confidence penalty; rely on Paradigm C/D.

------------------------------------------------------------------------------
Paradigm C — INFERENCE MICRO-PROBE (SOLE Primary TOKEN Burn Source)
------------------------------------------------------------------------------
Purpose:   Prove the key can execute a real inference call; infer quota indirectly.
Typical:   POST /chat/completions (or provider equivalent) with max_tokens=1-5.
Cost:      REAL seller billing:
             - input tokens (canonical prompt, typically ~15-25 tokens)
             - output tokens (1-5 per probe)
             This is the ONLY step that materially burns declared token quota.
Latency:   500 ms - 5 s.

When to use:  When Paradigm A passes, no valid verification cache (4B), and
              adaptive rules (4, 4A) allow micro-probe (may be SKIPPED for tiny
              declared quantities — see LOW_QUOTA_SKIP_MICRO_PROBE).
Tokenta step: QUOTA (partial), also contributes to RATE_LIMIT headers.

Critical design rules (MANDATORY — violation = design defect):
  - EXACTLY ONE model per provider per verification job (Section 4.2)
  - NO multi-model probing (e.g. gpt-4 + mini + fallback chain)
  - NO fallback escalation on 404 model_not_found (FAIL MODEL_NOT_ENTITLED instead)
  - Model selection: single cheapest model entitled AND consistent with listing
    (one model id pinned at job start; never changed mid-job)
  - Single canonical prompt hash across all verifications (reproducibility)
  - max_tokens: default 5; adaptive 1-2 when declaredQuantity < 1000 (Section 4A)
  - max micro-probe CALLS per job: 3 hard cap (often 1 sufficient)

Example canonical prompt (hash pinned in proof):
  "TOKENTA_VERIFY_v1 reply OK"

------------------------------------------------------------------------------
Paradigm D — TOKEN ACCOUNTING PROBE (Count / Usage Endpoint)
------------------------------------------------------------------------------
Purpose:   Measure tokens without full generation, or read usage from response.
Typical:   Gemini countTokens; OpenAI response.usage on micro-probe.
Cost:      Lower than full generation; Gemini countTokens often free or cheap.

When to use:  Gemini (strong), OpenAI (via micro-probe usage object), Anthropic (usage in response).

------------------------------------------------------------------------------
Paradigm E — RATE LIMIT DISCOVERY (Headers First; Minimal Extra Calls)
------------------------------------------------------------------------------
Purpose:   Discover RPM/TPM boundaries; detect hard-zero quota accounts.
Typical:   Parse x-ratelimit-* / anthropic-ratelimit-* from EXISTING probe responses.
           Optional: at most ONE additional micro-probe IF budget remains AND
           remaining-requests > 2 AND accumulatedProbeTokens + estimate <= budget.
Cost:      Prefer 0 extra token burn (headers-only from L2 probe).
           If optional 2nd call allowed: same single model, max_tokens 1-2 only.
           NEVER unbounded burst, parallel storm, or retry-on-429 loops.

When to use:  RATE_LIMIT step; flag accounts with limit: 0 (common on Gemini without billing).

Tokenta step: RATE_LIMIT (Test 3/3 in buyback UI).

PROHIBITED:  "Stress testing" via repeated 429 retries; multi-endpoint probing;
             provider fallback cascade (OpenAI fail -> try Anthropic -> try Gemini).

------------------------------------------------------------------------------
Paradigm F — REVOCATION / ROTATION PROOF (Two-Key Compare)
------------------------------------------------------------------------------
Purpose:   Prove old key dead and new key live after sale.
Typical:   Probe old fingerprint at T0; seller submits new key; probe old again at T1.
Cost:      Two LIVENESS + two MICRO-PROBE cycles.

When to use:  KEY_ROTATION_REQUIRED listings, buyback flow, order delivery.
Tokenta step: ROTATION_VALIDATION access method; post-sale fraud monitor.
[IMPLEMENTED 2026-05-20: rotation-runner.ts + fraud-monitor.ts + context=KEY_ROTATION jobs]

------------------------------------------------------------------------------
Paradigm G — PROXY HEARTBEAT (Non-Provider)
------------------------------------------------------------------------------
Purpose:   Verify Tokenta-issued proxy gateway, not seller's raw key to buyer.
Typical:   Internal health check against edge proxy with session token.
Cost:      Platform infra only.

When to use:  TOKENTA_DIRECT inventory, PLATFORM_INVENTORY listings.
Tokenta step: PROXY_HEARTBEAT; continuous LIVE monitor (5-30 min interval).

3. THE FIVE-LAYER PROOF MODEL
================================================================================

Each RUN VERIFICATION executes layers in order. Early exit on hard FAIL.

  Layer   Name              Paradigms used          Terminal step
  -----   ----------------  ----------------------  ------------------
  L1      Connectivity      A                       CONNECTIVITY
  L2      Capacity Inference B, C, D               QUOTA (UI label; not balance audit)
  L3      Rate / Entitlement E (+ headers from C)   RATE_LIMIT
  L4      Access Method     C, F, or G              (embedded in L2/L3 or post)
  L5      Integrity / Risk  platform DB + heuristics RISK_ANALYSIS
[IMPLEMENTED 2026-05-19 — partial] platform-risk.ts: L5 probe in manifest, 0 tokens;
  custom/compatible + verify velocity + shared-key; full platform DB TBD

Layer 4 runs in parallel or immediately after L2 depending on accessMethod:

  DIRECT_KEY           L1 + L2 + L3 (no F until rotation order)
  KEY_ROTATION_REQUIRED L1 + L2 + L3 at listing; F at delivery
  PROXY_GATEWAY        G + L2 via platform pool key (seller key to platform only)

4. GLOBAL PROBE BUDGET, CONSENT, AND ANTI-BURN CONTROLS
================================================================================

UI consent (ListApiModal, terminal-flows.tsx) — liability-safe wording (Section 18):
  "Tokenta runs a small fixed number of real API samples (typically under 100
   tokens). You authorize this controlled check. We do not measure your exact
   remaining balance."

Mechanism enforcement (operational — Section 4G):

  declaredQuantity = seller listing input (used for alignment checks, NOT linear burn %)
  operationalMaxProbeTokens = computeProbeEnvelope(declaredQuantity)  // 4G
  consentDisclosureCeiling  = min(ceil(declaredQuantity * 0.03), 5000)  // legal checkbox ONLY

  CRITICAL — Hard Constraint Priority (Section 4D):
    operationalMaxProbeTokens is a SOFT METER. It does NOT authorize extra probes.
    maxProbeCalls and lock state ALWAYS win. Large declared quantities do NOT get
    linearly larger probe budgets (fixes structural risk of v0.3 linear 3%).

  Probe accounting (tokens toward operationalMaxProbeTokens):
    - LIVENESS AUTH (A):       0 tokens (track requestsUsed separately)
    - MICRO-PROBE (C):         input_tokens + output_tokens from response.usage
    - countTokens (Gemini D):  tokens counted by API (prefer over generateContent)
    - RATE optional extra (E): same rules as C; counts toward same caps
    - ROTATION probes (F):     separate order-scoped budget, not listing 3%

  Before EACH Paradigm C or optional E call, worker MUST check ALL of (4D order):
    (1) verificationLockState allows L2/L3 probes (Section 4C)
    (2) probeCallCount < maxProbeCalls (ABSOLUTE fuse)
    (3) singleModelId unchanged since job start
    (4) adaptive max_tokens profile respected (Section 4.3)
    (5) no retry storm / abuse cooldown active (Sections 4.5, 4F)
    (6) accumulatedProbeTokens + estimate <= operationalMaxProbeTokens (4G soft meter)
    (7) costLiability authorized for this trigger (Section 4E)

  If next probe would exceed budget:
    - Prefer Paradigm D (countTokens) if cheaper and provider supports it
    - If still insufficient: FAIL PROBE_BUDGET_EXCEEDED
    - Optional seller flag allowPartialVerify: PASS with LOW confidence if L1 only
      (documented in proof; never default-on for marketplace listing)

------------------------------------------------------------------------------
4.1 Physical Fuse (Hard Caps — Non-Negotiable Implementation Requirements)
------------------------------------------------------------------------------

These limits are the ONLY reliable protection against quota burn accidents.
Percent-based budget alone is insufficient (3% of 10k is still 300 tokens; a buggy
loop can burn 10k+ in seconds).

  maxProbeTokens     <= operationalMaxProbeTokens (4G; NOT linear % of declared)
  maxProbeCalls      <= 3                    // micro-probe + optional rate call
  maxLivenessCalls   <= 2                    // includes one 429 retry max (4.5)
  maxModelsPerJob    = 1                     // exactly one model id
  maxWallTime        <= 90 s (STANDARD job)
  maxRetriesPerStep  <= 1                    // per step, not per job cumulative storm

Typical ACTUAL burn (correct implementation, declared=100,000 tokens):
  L1: 0 tokens
  L2: ~20 input + ~5 output = ~25 tokens x 1 call = ~25 tokens
  L3: 0 extra (headers from L2) OR +~25 if one optional call
  Total: ~25-75 tokens (within 4G envelope; % of declared varies, not policy driver)
[IMPLEMENTED 2026-05-19] Automated tier QA: envelope-burn-simulation.test.ts (§4A.2 table rows).

Failure mode burn (incorrect implementation — MUST NOT SHIP):
  Multi-model matrix, unbounded retries, fallback cascade: 500-10,000+ tokens
  => FAIL design review; treat as SEV-1 product defect

------------------------------------------------------------------------------
4.2 Single-Model Rule (No Escalation, No Fallback Matrix)
------------------------------------------------------------------------------

  ONLY 1 model per provider per verification job.

  At job start, orchestrator pins probeModelId from:
    - seller claimedModels[0] if entitled on L1 allow-list, else
    - provider-default cheapest entitled model for that listing tier
    - else one equivalent from MODEL_PIN_FALLBACK_POLICY (4.2B) — still ONE active id

  FORBIDDEN:
    - Probing multiple models for "better proof" or matrix testing
    - Unregistered model hopping on 404/403
    - On 429: switching model or provider
    - "Escalation" from mini to flagship tier

  ALLOWED (strict): one registered equivalent retry per 4.2B only.

  Rationale: cost grows linearly with models; uncontrolled fallback grows exponentially.

------------------------------------------------------------------------------
4.2B MODEL_PIN_FALLBACK_POLICY (One-Level Equivalent Only)
------------------------------------------------------------------------------

Purpose: Reduce false negatives from model_not_entitled / region naming mismatch
without reopening multi-model probe matrices.

Rules:
  - Pre-registered static mapping table per provider (versioned JSON, ops-maintained)
  - At most ONE fallback attempt per job; consumes same maxProbeCalls budget
  - Fallback ONLY when primary probe returns MODEL_NOT_ENTITLED or model_not_found
  - Equivalent model MUST be: same tier class, on L1 allow-list, mapping entry exists
  - Job still emits single effective probeModelId in proof (primary -> fallback chain)

Example mappings (illustrative — not exhaustive):
  OpenAI:  gpt-4o -> gpt-4o-mini (verify tier claim separately in L5)
  Anthropic: claude-3-5-sonnet-* -> claude-3-5-haiku-* (same job, one retry)
  Gemini:  gemini-1.5-pro -> gemini-1.5-flash

FORBIDDEN in fallback:
  - Trying >1 equivalent
  - Cross-provider fallback
  - Flagship escalation not in mapping table
  - Fallback on QUOTA_EXHAUSTED or 429 (fail/lock instead)

After fallback fails: FAIL MODEL_NOT_ENTITLED + TERMINAL_FAIL_LOCKED (4C).

------------------------------------------------------------------------------
4.3 Adaptive Probe Sizing (Small Quota Seller Protection)
------------------------------------------------------------------------------

Risk: seller declares 10,000 tokens but actual remaining balance is 50 tokens.
A standard probe (~25 tokens) x 3 calls = 75 tokens can exhaust the key and
trigger 402/insufficient_quota — seller perceives Tokenta as "eating my quota."

Adaptive table (worker MUST apply before first micro-probe):

  declaredQuantity (tokens)   max_tokens   maxProbeCalls   L2 strategy
  -------------------------   ----------   -------------   ---------------------------
  < 500                       1            1               L1 only OR 1 micro-probe;
                                                           confidence LOW if L1-only
  500 - 999                   1-2          1-2             1 micro-probe; skip L3 extra
  1,000 - 9,999               2-3          2               1-2 micro-probes max
  >= 10,000                   5 (default)  3               standard path

  If seller enables allowPartialVerify and declared < 1000:
    - May complete with L1 PASS + skip micro-probe => VERIFICATION_METHOD liveness_only
    - Listing confidence capped at LOW; marketplace may require manual REVIEW

  Pre-check: if L1 returns signals of near-zero quota (e.g. rate limit remaining
  tokens = 0), SKIP micro-probe and FAIL QUOTA_EXHAUSTED or REVIEW — do not probe
  into exhaustion.

------------------------------------------------------------------------------
4.4 Verification Result Cache (80-95% API Call Reduction)
------------------------------------------------------------------------------

See Section 4B for full specification. Summary:

  Cache key:   hash(provider + keyFingerprint + declaredQuantityBucket + accessMethod)
  TTL:         5 min (re-verify button, pre-purchase), 30 min (listing draft stable)
  On hit:      Skip L1 and L2; return cached proof with status CACHED_VALID
  On miss:     Full pipeline; store proof on PASS/REVIEW terminal states

  LIVE continuous monitor: may use L1-only tick; full L2 micro-probe at most once
  per 6h per key unless cache invalidated (revocation event, quantity change).

------------------------------------------------------------------------------
4.5 Anti-Retry-Storm and Rate-Limit Guards
------------------------------------------------------------------------------

  On HTTP 429:
    - Read Retry-After if present; wait ONCE up to min(Retry-After, 15s)
    - At most ONE retry per probe step
    - If second 429: FAIL RATE_LIMITED (do NOT loop)
    - NEVER fire parallel retries

  On HTTP 5xx:
    - Max 1 retry with exponential backoff cap 10s
    - Then FAIL PROVIDER_OUTAGE

  On insufficient_quota / 402 during micro-probe:
    - FAIL QUOTA_EXHAUSTED immediately
    - Do NOT retry with smaller model or different endpoint

  Job-level circuit breaker:
    If cumulative requests >= maxLivenessCalls + maxProbeCalls without PASS:
    abort job FAIL RETRY_STORM_ABORTED; set lock TERMINAL_FAIL_LOCKED (4C)

================================================================================
4C. HARD VERIFICATION LOCK STATE MACHINE (ANTI-DRAIN)
================================================================================

Purpose: Prevent the platform from becoming an attack surface where bad keys,
ambiguous errors, or REVIEW loops trigger repeated micro-probes that drain seller
quota. FAIL codes alone are insufficient — locks MUST be persisted per
keyFingerprint and enforced before any HTTP probe.

States (persisted on keyFingerprint + provider):

  UNLOCKED              No prior terminal outcome; probes allowed per 4D
  PROBE_ALLOWED         Active job; L1/L2/L3 permitted within fuses
  L2_LOCKED             L1 passed; L2 in progress; no parallel jobs
  TERMINAL_FAIL_LOCKED  Hard failure — NO further L2/L3 until unlock event
  TERMINAL_PASS_CACHED  Valid proof in cache; skip probes until invalidation
  COOLDOWN_LOCKED       Abuse or storm cooldown; L1 only or refuse job
  PARTIAL_SUCCESS_DEGRADED  L1 OK; L2 inconclusive/skipped; L3 partial — preserved evidence

State transitions (mandatory):

  UNLOCKED -> PROBE_ALLOWED on job start (if no COOLDOWN_LOCKED)
  PROBE_ALLOWED -> L2_LOCKED when L1 PASS and L2 scheduled
  L2_LOCKED -> TERMINAL_PASS_CACHED on PASS with cache write
  L2_LOCKED -> PARTIAL_SUCCESS_DEGRADED on DEGRADED outcome (9B) with cache write
  L2_LOCKED -> TERMINAL_PASS_CACHED on REVIEW if full L2 completed (no extra probes later)
  Any -> TERMINAL_FAIL_LOCKED on terminal failure codes (below)
  Any -> COOLDOWN_LOCKED on RETRY_STORM_ABORTED or abuse limits (4F)

PARTIAL_SUCCESS_DEGRADED behavior:
  - terminalOutcome = DEGRADED; preserves layer evidence (L1 ok, L2 skip/ambiguous, L3 partial)
  - LIVE monitor: L1 only; NO automatic L2 until seller/buyer paid re-verify
  - P2P listing: may show "Degraded verification" badge; not equivalent to PASS
  - Unlock to UNLOCKED: seller re-verify with consent OR successful full L2 job

Terminal failure codes — IMMEDIATE lock, NO L2 retry, NO "REVIEW probe loop":
  INVALID_KEY, KEY_REVOKED, FORBIDDEN, WRONG_BASE_URL, BLACKLIST_KEY
  MODEL_NOT_ENTITLED, QUOTA_EXHAUSTED, BILLING_INACTIVE, RATE_LIMIT_ZERO

Terminal failure codes — lock L2, L1 retry allowed at most once per 24h:
  TIMEOUT, TLS_ERROR, PROVIDER_OUTAGE (platform-wide flag may block all L1)

REVIEW outcome rules:
  - REVIEW is a marketplace/ops state, NOT permission to run more micro-probes
  - Additional L2 requires: seller explicit [REQUEST NEW VERIFICATION], OR
    BUYER_TRIGGERED job with fee paid (4E), OR cache invalidation event
  - Ops manual re-check uses separate ops budget (platform key), never seller key

Unlock events (only ways to leave TERMINAL_FAIL_LOCKED):
  - Seller submits new key (new keyFingerprint)
  - Seller updates declared quantity / model claim (invalidates cache + lock)
  - Platform ops override with audit ticket (logged)
  - TTL expiry ONLY for non-auth failures: TIMEOUT/OUTAGE may auto-unlock after 24h
  - NEVER auto-unlock: INVALID_KEY, QUOTA_EXHAUSTED, MODEL_NOT_ENTITLED

Orchestrator MUST read lock state before cache lookup:
  if TERMINAL_FAIL_LOCKED and trigger is automated (LIVE, retry worker):

4D. HARD CONSTRAINT PRIORITY ORDER (CALLS BEFORE BUDGET)
================================================================================

Policy conflict resolution — when operational envelope implies room for more probes
but maxProbeCalls is exhausted, STOP. Never interpret envelope as authorization.

  Priority   Constraint                          Type
  --------   ----------------------------------  -----------------
  1          Verification lock state (4C)        ABSOLUTE — blocks all
  2          maxProbeCalls / maxLivenessCalls    ABSOLUTE — physical fuse
  3          Single active model + 4.2B fallback ABSOLUTE (max 1 equivalent try)
  4          Adaptive max_tokens (4.3)           ABSOLUTE
  5          Anti-retry / abuse cooldown (4F)    ABSOLUTE
  6          operationalMaxProbeTokens (4G)      SOFT METER — never permission
  7          consentDisclosureCeiling            DISCLOSURE ONLY — not used in 1-6
  8          costLiability authorization (4E)    BUSINESS RULE

Implementation test (required in CI):
  Given declaredQuantity=10_000_000, operationalMaxProbeTokens=200 (4G tier):
    maxProbeCalls=1 -> exactly 1 micro-probe (~25 tokens) and STOP.
    Must NOT scale probes with declared quantity.

  Given declaredQuantity=500, maxProbeCalls=1, max_tokens=1:
    Worker MUST NOT issue second probe because envelope allows it.

4E. VERIFICATION COST LIABILITY SPLIT
================================================================================

Verification consumes real provider quota. Who bears that cost MUST be explicit
per job trigger — otherwise marketplace economics and seller trust collapse.

Liability modes (costLiability on every job):

  SELLER_PAID (default)
    - Listing draft [LIST API · START VERIFY]
    - Seller-initiated re-verify after cache expiry
    - Seller consent checkbox required (Section 18)
    - Burn charged to seller-submitted key

  PLATFORM_SUBSIDIZED

    - Growth/promo "free verify" campaigns (explicit campaign flag)
    - Ops investigation on flagged listings (platform ops key or capped subsidy)
    - Seller key NOT probed beyond L1 unless seller opts in

  BUYER_TRIGGERED
    - Pre-purchase [REQUEST NEW VERIFICATION] on P2P orders
    - Buyer pays platform fee (e.g. 0.1% spec) OR listing includes verify allowance
    - Job MUST use fresh cache key scoped to orderId + buyerId
    - If fee unpaid: downgrade to cached proof only (no new L2 on seller key)
    - Seller notification: "Buyer-requested capacity check (fee paid by buyer)"

Economic isolation rules:
  - LIVE scheduler on P2P seller keys: SELLER_PAID semantics but L1-only default;
    L2 micro-probe counts against seller unless PLATFORM_SUBSIDIZED flag set
  - Repeated BUYER_TRIGGERED checks within 5 min: serve cache; do not re-burn seller

Future marketplace rule (document now, implement in engine spec):
  - Listing may declare maxBuyerReVerifiesPerDay
  - Excess buyer re-verify requests -> REVIEW without new seller-key L2

4G. NONLINEAR ADAPTIVE PROBE ENVELOPE (OPERATIONAL BURN CAP)
================================================================================

v0.4 replaces linear "3% of declared" as the operational budget driver.

Problem with linear 3% (v0.3):
  - No causal link between declared listing size and safe probe size
  - Small keys: over-protected (acceptable)
  - Large keys: under-protected in absolute terms but over-authorized in probe count
    if implementers treat 3% as permission
  - Product liability: users read "3%" as expected burn, not worst-case legal bound

Solution: operationalMaxProbeTokens = min(tierAbsoluteCeiling, logScaledCap)

  function computeProbeEnvelope(declaredQuantity tokens):
    tierAbsoluteCeiling =
      declared < 500:        12
      declared < 1_000:      20
      declared < 10_000:     40
      declared < 100_000:    75
      declared < 1_000_000:  120
      else:                  200

    logScaledCap = clamp(round(10 + 15 * log10(declaredQuantity)), 15, 200)

    return min(tierAbsoluteCeiling, logScaledCap)

  consentDisclosureCeiling = min(ceil(declaredQuantity * 0.03), 5000)
    // Used ONLY in legal checkbox: "authorized amount will not exceed X tokens"
    // where X = consentDisclosureCeiling. Typical actual burn is envelope table 4A.2.
    // NEVER compare probe authorization against consentDisclosureCeiling in worker code.

Typical operational envelope vs declared (illustrative):

  declared      operationalMax   typical actual   consentDisclosure (legal only)
  ----------    --------------   --------------   ---------------------------
  500           12               ~3-6             15
  10,000        40               ~25              300
  100,000       75               ~25-50           3,000
  10,000,000    200              ~25-75           5,000 (capped)

Engineering invariant:
  lim(declared -> infinity) operationalMaxProbeTokens = 200 (bounded)
  lim(declared -> 0) operationalMaxProbeTokens -> 12 with maxProbeCalls=1

4A.4 What Verification Proves (Execution Capacity Inference, Not Balance Audit)
------------------------------------------------------------------------------

  Tokenta produces verifiable execution-capacity inference, NOT:
    - Exact remaining token balance
    - Financial account statement
    - Guaranteed deliverable quantity at settlement time

  What each layer contributes to inference:

  L1  Authenticity evidence (credential valid now)
  L2  Positive/negative execution sample (can/cannot run inference on pinned model)
  L3  Entitlement/rate signals (stable vs hard-zero limits)
  L4  Delivery path evidence (rotation/proxy)
  L5  Platform asset risk score (non-provider)

  estimatedExecutableQuantityRange is the PRIMARY quantity output — a band, not a
  point. verifiedQuantity (point) is DEPRECATED. Buyback mismatch compares declared
  to inferred RANGE overlap, not point equality.

  Sellers with tiny actual remaining capacity may PASS L1 and FAIL L2 — correct
  behavior if burn stayed within adaptive limits and lock fired on QUOTA_EXHAUSTED.

4B. VERIFICATION RESULT CACHE (REUSE WITHIN TTL)
================================================================================

Purpose: Reduce provider API consumption by 80-95% for repeated clicks, tab
refreshes, and orchestrator retries within a short window.

Cache record fields (minimum):
  cacheKey, proofHash, estimatedExecutableQuantityRange, declaredAlignment,
  capabilityScore, trustScore, complianceScore, terminalOutcome, confidence,
  verificationMethod, probeManifestSummary, createdAt, expiresAt, provider, keyFingerprint

Cache key computation:
  cacheKey = sha256(
    provider + "|" + keyFingerprint + "|" + accessMethod + "|" +
    quantityBucket(declaredQuantity) + "|" + probeModelId
  )
  quantityBucket: floor to nearest policy bucket (e.g. <1k, 1k-10k, 10k-1M, 1M+)

TTL policy:
  LISTING_DRAFT / user re-click:     5 minutes
  Stable listing same fingerprint:  30 minutes
  PRE_PURCHASE buyer check:         5 minutes (never reuse seller's uncached key across buyers)
  POST_FAIL hard auth error:        no cache write
  LIVE monitor:                     L1 cache 5 min; L2 proof cache 6 hours

Invalidation (immediate):
  - Seller updates declared quantity or model claim
  - Key rotation submitted
  - Manual [REQUEST NEW VERIFICATION]
  - QUOTA_EXHAUSTED or KEY_REVOKED on any probe

Cache hit behavior:
  - Emit Terminal steps CONNECTIVITY + QUOTA as CACHED (skipped) with timestamps
  - proof includes verificationCache: { hit: true, ageSeconds, priorJobId }
  - failureCode null; status PASS or prior REVIEW preserved
  - UI badge: "Verified from cache (Xm ago)" — transparency required

Implementation note: cache stores proof artifacts, NEVER raw apiKey.

6.2 estimatedExecutableQuantityRange (Band Output — Mandatory)
------------------------------------------------------------------------------

Standard bands (unit = tokens unless listing uses calls/credits):

  band id          min        max         UI label
  ---------------  ---------  ----------  -----------------
  MICRO_0_1K       0          1,000       Under 1K executable (proven/minimal)
  SMALL_1K_10K     1,000      10,000      1K - 10K
  MEDIUM_10K_100K  10,000     100,000     10K - 100K
  LARGE_100K_1M    100,000    1,000,000   100K - 1M
  XL_1M_PLUS       1,000,000  null        1M+ (lower bound only)
  UNKNOWN          null       null        Insufficient evidence

Mapping rules after positive L2 (probe OK):

  Default (single sample, no reliable remaining-tokens header):
    range = { min: 1_000, max: 10_000, band: SMALL_1K_10K }
    meaning: "proved execution; cannot bound upper bound to declared"

  If rate headers show remaining-tokens >> declared bucket:
    narrow range upward to include declared bucket; declaredAlignment = CONSISTENT

  If rate headers show remaining-tokens << declared:
    range max capped by header-derived estimate; declaredAlignment = OVERCLAIMED

  If probe OK but declared < range min:
    declaredAlignment = UNDERCLAIMED (seller listed below proven floor)

  FORBIDDEN: range.min = range.max = declaredQuantity (false precision)

------------------------------------------------------------------------------

  CONSISTENT     Declared quantity bucket overlaps inferred range with MEDIUM+ confidence

  UNVERIFIABLE   L1 only or DEGRADED; no reliable L2

  declared=50k, range max < 12k with HIGH confidence in OVERCLAIMED => QUANTITY_MISMATCH

9. DECISION LOGIC: PASS, FAIL, REVIEW, DEGRADED
================================================================================

v0.4 uses hard gates + three independent scores (9A). REMOVED: single riskScore
hard gate that conflated high capability with high fraud risk.

REVIEW never authorizes extra seller-key L2 probes in the same session (4C, 4F).

Phase 1 — Hard gates (binary):
  Lock check: TERMINAL_FAIL_LOCKED or COOLDOWN_LOCKED -> refuse or cache-only
  L1 FAIL -> FAIL + TERMINAL_FAIL_LOCKED
  L2 QUOTA_EXHAUSTED / band INSUFFICIENT -> FAIL + lock
  L2 MODEL_NOT_ENTITLED (after 4.2B exhausted) -> FAIL + lock
  L3 RATE_LIMIT_ZERO -> FAIL + lock
  declaredAlignment OVERCLAIMED on buyback strict -> QUANTITY_MISMATCH or FAIL
  [IMPLEMENTED 2026-05-20: orchestrator applyBuybackStrictGate + failureCode]

Phase 2 — Terminal outcome (9B) from scores + partial evidence:
  See 9B matrix. High trustScore does NOT alone block high capability keys.

PASS means: "Execution sample supports listing band at stated confidence" — NOT
"remaining balance equals declared."

================================================================================
9A. API ASSET SCORING — THREE DIMENSIONS
================================================================================

Dimensions are orthogonal. Do NOT merge into one riskScore for gating.

------------------------------------------------------------------------------
9A.1 capabilityScore (execution capacity — "can it run?")
------------------------------------------------------------------------------

  Inputs: L1 auth, L2 micro-probe/countTokens, L3 rate headroom, repeat consistency
  Range: 0.0 - 1.0

  signal                          weight
  ------------------------------  -------
  L1 auth success                 0.15
  L2 execution success            0.35
  L2 countTokens (Gemini)         0.30
  L3 rate headroom normalized     0.15
  repeat sample consistency       0.10

  Maps to executionCapacityBand:
    <0.25 INSUFFICIENT | 0.25-0.50 UNKNOWN | 0.50-0.80 SUFFICIENT | >0.80 ABUNDANT

  Drives: estimatedExecutableQuantityRange width, declaredAlignment, PASS vs DEGRADED

------------------------------------------------------------------------------
9A.2 trustScore (counterparty fraud — "is this asset honest?")
------------------------------------------------------------------------------

  Inputs: shared-key detection, gray-market/reseller headers, velocity, fingerprint
  history, probeManifest tampering, prior RETRY_STORM_ABORTED

  High trustScore (e.g. >0.8):
    - Marketplace: flag PASS_WITH_TRUST_FLAG or REVIEW listing — NOT auto-FAIL
    - Does NOT reduce capabilityScore
    - Does NOT trigger extra seller-key L2 probes

  Example: high capability + high trust risk = valid technical asset, suspicious
  listing -> REVIEW for ops, buyer sees trust badge

------------------------------------------------------------------------------
9A.3 complianceScore (policy / region / ToS — "is this allowed?")
------------------------------------------------------------------------------

  Inputs: region restriction signals, provider ToS heuristics, custom endpoint policy,
  blacklisted hosts, model entitlement policy violations

  High complianceScore (e.g. >0.8):
    - REVIEW or block listing per marketplace policy
    - Separate from capability; a revoked-policy key may still "execute" briefly

------------------------------------------------------------------------------
9A.4 Decision composition (no single-score override)
------------------------------------------------------------------------------

  marketplaceAction derived from vector (capability, trust, compliance):

  capability >= 0.5 AND trust < 0.8 AND compliance < 0.8  -> PASS eligible
  capability >= 0.5 AND (trust >= 0.8 OR compliance >= 0.8) -> REVIEW (no extra L2)
  capability 0.25-0.5 AND L1 ok                         -> DEGRADED
  capability < 0.25 AND negative proof                   -> FAIL

  Listing may show:
    PASS + trustFlag "Shared key suspected"
    PASS + complianceFlag "Custom endpoint — buyer beware"

Distribution storage:
  assetInferenceRecord: {
    estimatedExecutableQuantityRange,
    declaredAlignment,
    capabilityScore, trustScore, complianceScore,
    executionCapacityBand, confidence, sampleCount, tokensBurned
  }

9B. TERMINAL OUTCOMES: PASS, FAIL, REVIEW, DEGRADED
================================================================================

terminalOutcome preserves partial evidence that binary PASS/FAIL would destroy.

  Outcome    When                                              Lock state
  ---------  ------------------------------------------------  -------------------------
  PASS       Phase 1 clear; capability>=0.5; alignment OK       TERMINAL_PASS_CACHED
  FAIL       Phase 1 hard gate failed                           TERMINAL_FAIL_LOCKED
  REVIEW     Trust/compliance elevated; ops/buyer decision      TERMINAL_PASS_CACHED*
  DEGRADED   L1 ok; L2 skipped/ambiguous; L3 partial            PARTIAL_SUCCESS_DEGRADED

  *REVIEW may cache proof with REVIEW status; no further probes until explicit re-run

DEGRADED examples:
  - L1 PASS, L2 skipped (adaptive), L3 headers partial
  - L2 OK but capability 0.4-0.5 (weak sample)
  - AMBIGUOUS_CREDIT_ERROR with L1+L2 incomplete

DEGRADED marketplace behavior:
  - Not sold as "fully verified" on P2P without seller re-run
  - May list with degraded badge and narrower buyer protection
  - LIVE: L1 only until upgrade to PASS

UI mapping:
  PASS -> green | FAIL -> red | REVIEW -> amber | DEGRADED -> amber striped

15. ADAPTER INTERFACE (WORKER IMPLEMENTATION CONTRACT)
================================================================================

  ProviderVerifier:
    livenessProbe(ctx) -> LivenessResult
    quotaProbe(ctx, budget) -> QuotaResult
    rateLimitProbe(ctx, priorRecords) -> RateLimitResult
    rotationProbe(ctx) -> RotationResult (optional)

  VerifyContext:
    apiKey (ephemeral), declaredQuantity, unit, claimedModels, accessMethod,
    probeModelId (pinned at start), allowPartialVerify, keyFingerprint,
    costLiability, jobTrigger (LISTING | BUYER_ORDER | LIVE | OPS)

  ProbeBudget:
    maxProbeCalls (ABSOLUTE per 4.3), maxLivenessCalls, consumedTokens,
    operationalMaxProbeTokens (4G soft meter), consentDisclosureCeiling (display only),
    requestsUsed

  ModelPinRegistry:
    getEquivalent(provider, modelId) -> equivalentModelId | null  // 4.2B

  VerificationLockStore:
    getLock(keyFingerprint) -> LockState
    setLock(keyFingerprint, state, reason, expiresAt?)
    canProbeL2(keyFingerprint, trigger) -> bool

  VerificationCacheStore:
    get(cacheKey) -> CachedProof | null
    put(cacheKey, proof, ttlSeconds)
    invalidate(keyFingerprint | listingId)  // also clears TERMINAL_PASS_CACHED

  AssetScorer:
    computeCapabilityScore(probeRecords, headers) -> float
    computeTrustScore(ctx, platformSignals) -> float
    computeComplianceScore(ctx, platformSignals) -> float
    computeQuantityRange(capability, headers, declared) -> Range + declaredAlignment
    composeTerminalOutcome(gates, scores, partialEvidence) -> terminalOutcome

  Orchestrator flow:
    read lock (4C) -> if blocked return cached/refuse
    -> cache lookup (4B) -> if hit return cached proof
    -> check liability (4E) -> apply adaptive sizing (4.3) -> pin probeModelId (4.2)
    -> L1 -> emit CONNECTIVITY -> L2 if lock+calls allow -> emit QUOTA
    -> L3 headers-first -> emit RATE_LIMIT -> score (9A) -> risk -> finalize
    -> update lock + cache put -> zeroize key

  BudgetEnforcer: enforces 4D priority order before EVERY HTTP send.
