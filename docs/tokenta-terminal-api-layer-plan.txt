1. EXECUTIVE SUMMARY
================================================================================

The Terminal is a stream-first product: users run verification, watch progress,
retrieve proofs, and (Phase 5A) receive on-chain execution receipts on testnet.

This document defines a **Terminal-facing API Layer** — a stable, product-shaped
contract on top of the existing Verification Engine. It is not a second engine;
it is the **facade** the UI, future CLI (`tokenta proof <job-id>`), and Swagger
documentation will target.

Design principles:
  1. Terminal namespace first:  /api/v1/terminal/*
  2. SSE first for execution streams; WebSocket deferred
  3. Explicit terminal job lifecycle (includes anchoring as first-class state)
  4. Execution Receipt as the canonical “run finished” artifact (product soul)
  5. Testnet settlement on **Base Sepolia** before any mainnet
  6. Three wallet roles: User (Privy), Treasury (backend signer), Escrow (future)

Implementation order (agreed roadmap):
  Phase 5A — Terminalization (now)     → this document
  Phase 5B — Live worker infrastructure → regional Redis/BullMQ, Docker
  Phase 5C — Production security       → Vault/KMS, TEE/ZK, HSM, slashing

2. RELATIONSHIP TO EXISTING VERIFICATION API
================================================================================

Today the Terminal calls engine routes directly (via Vite proxy):
  POST /api/v1/verification/jobs
  GET  /api/v1/verification/jobs/{id}
  GET  /api/v1/verification/jobs/{id}/events   (SSE)
  GET  /api/v1/verification/proofs/{proofHash}

The Terminal API Layer will **delegate** to these internally during 5A, then
optionally absorb them behind a versioned facade. Mapping strategy:

  Terminal route                    Engine route (5A adapter)
  ------------------------------    ------------------------------------------
  POST /terminal/session            (new) session store + Privy binding
  POST /terminal/run                POST /verification/jobs (+ enrich)
  GET  /terminal/job/{id}           GET  /verification/jobs/{id}
  GET  /terminal/job/{id}/events    GET  /verification/jobs/{id}/events
  GET  /terminal/proof/{id}         GET  /verification/proofs/{proofHash}
                                    or GET /terminal/job/{id}/receipt
  GET  /terminal/receipt/{jobId}    (new) execution receipt aggregate

Engine-only routes remain for marketplace, admin, metrics:
  /api/v1/listings/*, /market/listings, /orders/*, /admin/*, /metrics/*

4. TERMINAL SESSION API
================================================================================

Purpose: Bind Privy user identity to server-side session, rate limits, audit,
and optional wallet address used for bind/escrow signatures.

4.1 POST /api/v1/terminal/session

  Description: Create or refresh a terminal session after Privy login.

  Request headers:
    Authorization: Bearer <privy-access-token>   (when PRIVY_JWT_VERIFY=true)
    X-Wallet-Address: 0x...                      (optional; must match JWT claim)

  Request body (optional):
    {
      "client": "web-terminal",
      "clientVersion": "0.1.0",
      "walletAddress": "0x..."
    }

  Response 201:
    {
      "sessionId": "tsess_...",
      "walletAddress": "0x...",
      "expiresAt": "2026-05-20T12:00:00.000Z",
      "capabilities": ["verify", "proof", "receipt"]
    }

  Errors:
    401  invalid or missing auth
    403  wallet mismatch vs JWT

  Notes:
    - Replaces ad-hoc VITE_API_DEV_TOKEN + X-Wallet-Address for Terminal-only flows
    - Dev mode: API_DEV_TOKEN may map to synthetic session (documented in runbook)
    - Session used for: POST /terminal/run, receipt download, anchor status polling

4.2 GET /api/v1/terminal/session

  Description: Introspect current session (from Authorization or session cookie).

  Response 200: same shape as create (without rotating sessionId unless configured).

4.3 DELETE /api/v1/terminal/session

  Description: Logout / invalidate server session record.

  Response 204.

5. TERMINAL RUN API (START EXECUTION)
================================================================================

5.1 POST /api/v1/terminal/run

  Description: Product entry point for “run verification” — maps to engine job
  creation with terminal lifecycle and receipt placeholder.

  Requires: valid terminal session (or dev token).

  Request body:
    {
      "mode": "verify",                    // verify | buyback | pre_purchase | rotation | live
      "provider": "openai",                // openai | anthropic | gemini
      "declaredQuantity": 10000,
      "claimedModel": "gpt-4o-mini",
      "costLiability": "SELLER_PAID",
      "listingId": "lst_...",              // optional
      "orderId": "ord_...",                // optional; required for rotation / pre_purchase
      "credential": {
        "type": "inline",                  // inline | vault_ref
        "apiKey": "sk-..."                 // inline only; never logged; never in receipt
      },
      "options": {
        "l1Only": false,
        "stream": true                     // hint: client will open SSE
      }
    }

  Context mapping (mode → engine context):
    verify         → LISTING_DRAFT
    buyback        → TOKENTA_BUYBACK
    pre_purchase   → PRE_PURCHASE
    rotation       → KEY_ROTATION
    live           → LIVE

  Response 202 Accepted:
    {
      "jobId": "vj_...",
      "terminalJobId": "tjob_...",         // stable terminal id (may equal jobId in 5A)
      "status": "queued",
      "streamUrl": "/api/v1/terminal/job/tjob_.../events",
      "receiptUrl": "/api/v1/terminal/receipt/tjob_...",
      "proofUrl": null,
      "createdAt": "..."
    }

  Errors:
    400  validation
    401  session
    429  abuse guard (§4F)
    503  queue saturated

5.2 POST /api/v1/terminal/run/{jobId}/cancel  (optional 5A.1)

  Description: User-cancel while queued or running (engine CANCELLED).

  Response 200: { "status": "cancelled" }

6. TERMINAL JOB LIFECYCLE
================================================================================

Terminal exposes a **product lifecycle** distinct from engine internal status.
Engine keeps: QUEUED | RUNNING | PASSED | FAILED.
Terminal adds human-facing phases including on-chain anchoring.

6.1 Terminal status enum

  queued       Job accepted; not yet picked up by worker
  running      Worker claimed job; connectivity / quota steps
  verifying    L1/L2 probes executing (orchestrator active)
  anchoring    Proof ready; settlement signer submitting Base Sepolia tx
  completed    Receipt available; terminalOutcome PASS/REVIEW/DEGRADED
  failed       Terminal FAIL or infrastructure error
  cancelled    User or ops cancelled

6.2 State transition diagram

  queued → running → verifying → anchoring → completed
                ↓         ↓           ↓
              failed    failed      failed
  queued → cancelled

  Rules:
    - verifying:  set when step CONNECTIVITY or QUOTA starts (SSE step_started)
    - anchoring:  set when proof exists and anchor tx submitted (or mock pending)
    - completed:  receipt.finalizedAt set; includes proof_hash + optional anchor_tx
    - failed:     engine FAILED or anchor permanently failed after retries

6.3 GET /api/v1/terminal/job/{terminalJobId}

  Description: Poll job status (SSE preferred; poll fallback).

  Response 200:
    {
      "terminalJobId": "tjob_...",
      "jobId": "vj_...",
      "status": "verifying",
      "progress": {
        "step": "QUOTA",
        "stepsCompleted": 2,
        "stepsTotal": 5,
        "percent": 40
      },
      "terminalOutcome": null,
      "proofHash": null,
      "anchor": {
        "chainId": 84532,
        "network": "base-sepolia",
        "status": "pending",
        "txHash": null
      },
      "startedAt": "...",
      "updatedAt": "..."
    }

  When completed, includes:
      "terminalOutcome": "PASS",
      "proofHash": "0x...",
      "receiptUrl": "/api/v1/terminal/receipt/tjob_..."

6.4 Mapping table: terminal status ← engine

  Engine status + step/event          Terminal status
  --------------------------------    ----------------
  QUEUED                              queued
  RUNNING, step CONNECTIVITY/QUOTA    running
  RUNNING, step RATE_LIMIT/RISK/...   verifying
  PASSED, anchor PENDING              anchoring
  PASSED, anchor CONFIRMED            completed
  PASSED, no anchor configured        completed (anchor skipped)
  FAILED                              failed
  CANCELLED                           cancelled

7. STREAMING EXECUTION (SSE FIRST)
================================================================================

7.1 GET /api/v1/terminal/job/{terminalJobId}/events

  Description: Server-Sent Events stream for terminal job execution.

  Headers:
    Accept: text/event-stream
    Last-Event-ID: <id>              (reconnect)

  Event types (terminal layer — superset of engine §22):
    session_bound
    job_queued
    job_running
    step_started
    step_completed
    step_failed
    job_verifying
    proof_ready
    anchor_submitted
    anchor_confirmed
    anchor_failed
    job_completed
    job_failed
    stream_end

  Example SSE payload:
    id: 42
    event: step_started
    data: {"terminalJobId":"tjob_...","step":"QUOTA","message":"Probing capacity","timestamp":"..."}

  Implementation plan (5A):
    - Adapter wraps existing GET /verification/jobs/{id}/events
    - Injects terminal status transitions and anchor events from proof-anchor service
    - Same backpressure and reconnect semantics as engine SSE

7.2 WebSocket (deferred — Phase 5B+)

  Path (reserved, not implemented in 5A):
    WS /api/v1/terminal/ws?sessionId=...

  Use when: multi-tab sync, bidirectional cancel, or sub-100ms step fanout required.

9. EXECUTION RECEIPT (PRODUCT SOUL)
================================================================================

The Execution Receipt is the terminal-native summary of a finished run. It is
what users export, what disputes reference, and what anchoring extends.

9.1 GET /api/v1/terminal/receipt/{terminalJobId}

  Description: Canonical receipt after status = completed (or failed with partial).

  Response 200:
    {
      "receiptVersion": "1.0",
      "job_id": "vj_...",
      "terminal_job_id": "tjob_...",
      "session_id": "tsess_...",
      "wallet_address": "0x...",
      "provider": "openai",
      "model": "gpt-4o-mini",
      "verified": true,
      "terminal_outcome": "PASS",
      "proof_hash": "0x...",
      "proof_url": "/api/v1/terminal/proof/0x...",
      "anchor": {
        "network": "base-sepolia",
        "chain_id": 84532,
        "contract": "0x...",
        "anchor_tx": "0x...",
        "anchor_status": "confirmed",
        "anchored_at": "..."
      },
      "cost": {
        "liability": "SELLER_PAID",
        "tokens_used": 42,
        "estimated_usdc": "0.24",
        "currency": "USDC"
      },
      "timing": {
        "queued_at": "...",
        "started_at": "...",
        "completed_at": "...",
        "duration_ms": 12400
      },
      "scores": {
        "capability": 0.82,
        "trust": 0.91,
        "compliance": 1.0
      },
      "signature": null
    }

  Field notes:
    - verified: true when terminal_outcome in (PASS, REVIEW, DEGRADED) per policy
    - anchor_tx: null until anchoring completes; receipt may be re-fetched
    - cost.estimated_usdc: platform estimate; not on-chain billing in 5A
    - signature: reserved for receipt ECDSA or EIP-712 in Phase 5C

9.2 POST /api/v1/terminal/receipt/{terminalJobId}/export  (optional 5A.1)

  Returns application/pdf or text/markdown export for support tickets.

11. WALLET & SIGNING ARCHITECTURE
================================================================================

Privy solves user login — not protocol settlement. Tokenta requires three wallet
roles.

11.1 Wallet type 1 — User Wallet (Privy — largely done)

  Purpose:
    - User login and identity
    - Session binding (POST /terminal/session)
    - Future: reputation, staking, billing
    - Client-side: bind-verification HMAC, escrow fund/release signatures

  Integration:
    - Terminal: @privy-io/react-auth → access token → Authorization header
    - Server: privy-jwt.ts / privy-jwks.ts (existing)
    - Headers: X-Wallet-Address synced from useTokentaWallet (existing)

  5A work: formalize session binding; stop relying only on dev token in prod path.

11.2 Wallet type 2 — Treasury / Platform Wallet (5A — must build)

  Purpose:
    - anchorProofHash submission
    - pay gas on Base Sepolia
    - future: escrow movement, protocol ops

  Must NOT use Privy embedded wallet for backend ops.

  MVP architecture (Phase 5A):
    verification-worker / anchor service
        ↓
    wallet-service (new module)
        ↓
    viem createWalletClient({ account, chain: baseSepolia, transport: http })
        ↓
    Base Sepolia RPC

  Env (server only, secret manager in 5C):
    TREASURY_PRIVATE_KEY=0x...
    SETTLEMENT_RPC_URL=...
    SETTLEMENT_CONTRACT_ADDRESS=0x...

  Safety (5A minimum):
    - Key never logged; never returned in API
    - Rate limit anchor submits per proofHash
    - Dry-run mode: SETTLEMENT_DRY_RUN=true (simulate tx, no broadcast)
    - Separate process optional: anchor-worker only signs

11.3 Wallet type 3 — Escrow / Order Wallet (future)

  Purpose: USDC escrow fund/release on-chain (beyond current signed API mock).

  5A: keep HTTP escrow API + signatures; document on-chain escrow as 5B/5C.

11.4 Who signs what

  Action                          Signer
  ------------------------------  ---------------------------------
  User login                      Privy (user wallet)
  POST /terminal/session          Server validates Privy JWT
  POST /terminal/run              Session + optional seller apiKey in body
  bind-verification               User HMAC (bind-signature.ts — existing)
  escrow fund/release             User HMAC (escrow-signature.ts — existing)
  anchorProofHash on testnet      Treasury (viem walletClient)
  Receipt integrity (future)      Platform ECDSA or EIP-712 over receipt hash

11.5 Terminal execution ↔ wallet identity binding

  Every terminal job record stores:
    sessionId, walletAddress (from session), optional listingId/orderId

  Receipt includes wallet_address for audit and dispute.

  Rule: POST /terminal/run rejects wallet mismatch if session wallet != body.
